# raw-write — 論文・申請書ジェネレータ

研究モードの執筆部スキル。論文・申請書・要旨などを、**本人の文体で・引用整合を保って**書く。就活の書類スキル `raw-es` の研究側の対応物。

## いつ使うか

- `/raw-write` を実行したとき
- 「論文を書いて」「Introduction を書いて」「Discussion を直して」「申請書を書いて」「学振の研究計画を書いて」「要旨を作って」「査読コメントへの返信」「カバーレター」と言われたとき
- 投稿先・申請区分・字数・セクションを渡されたとき
- 「私の文体で書いて」「文体を学習して」と言われたとき（→「文体プロファイル」 `work/manuscripts/_style/`）

`office/`（研究モード）が無ければ `/raw` で研究トラックのセットアップを促す。 **また、office 冒頭が `> トラック: 就活` の場合は「これは研究向けのスキルです。就活プロジェクトのようなので raw-research（企業研究）や raw-es 等をご利用ください」と伝え、無理に進めない。**writing 部署が未作成なら作成を提案する。

## はじめてモードを尊重する

このスキルを実行する前に `office/AGENTS.md`（Claude Code では `CLAUDE.md`）を読み、冒頭に `> 運用モード: はじめて` があれば、`raw` skill の「はじめてモードの挙動」を全応答に適用する：**平易な日本語**で話し、専門用語（IMRaD・hedging・査読・科研費・自己評価 等）は初出で 1 行説明を添え、各ステップの最後に**「次はこれをしましょう」を 1 つ**だけ提示する。元に戻せない操作（上書き・外部送信）は必ず事前確認する。

## ワークフロー

`${SKILL}` = このスキルの install 位置（各 CLI のプラグイン配下の `skills/raw-write/`）。以下のコマンドの `${SKILL}` を実パスに置換して実行する。Windows では `python3` を `py` に読み替える。

### Step 1: 文書種別・要件を確認

次を確認する（不足は `AskUserQuestion` で聞く）：

- **文書種別**（下表）
- **言語**（論文＝英語を既定 / 申請書＝日本語を既定。ユーザーの明示があれば従う）
- **対象**（論文＝投稿先の誌名や分野 / 申請書＝制度名・区分〔学振 DC/PD・科研費・民間財団〕）
- **範囲**（フル / セクション単位 / 特定の設問・欄）
- **字数・語数制限**（あれば厳守。申請書は欄ごとに字数が違うことが多い）

| 種別 | 主なセクション・型 |
|---|---|
| **論文**（manuscript） | Title / Abstract / Introduction / Results / Discussion / Methods / Conclusion（IMRaD）。カバーレター・査読回答（response to reviewers）も含む |
| **申請書**（grant / fellowship） | 研究の背景・目的 / 学術的問い / 研究計画・方法 / 独自性・創造性 / 期待される成果 / 自己評価（研究遂行能力）。制度の様式に従う |
| **学会要旨**（abstract） | 背景 → 目的 → 方法 → 結果 → 結論 を字数内に圧縮 |
| **その他**（報告書・英文レター 等） | 結論先出し → 具体 → まとめ |

### Step 2: 素材を集める

- **`work/manuscripts/_style/`（文体プロファイル。`raw-intake` が自分の論文から抽出）があれば必ず読み、その文体（トーン・一文の長さ・hedging・構成の癖）で書く。** 無ければ統合 `inbox/` の自分の過去論文を直接読む。それも無ければ中立な学術文体で書き、「過去の自分の文章を `inbox/` に入れると文体を学べます」と一言添える。
- **`work/manuscripts/_style/writing-preferences.md`（推敲で学んだ好み）があれば必ず読み、文体プロファイルの上に重ねて先回り適用する**（例:「能動態を優先」「『〜と考えられる』を多用しない」「結論は冒頭 1 文」「避ける語」）。前回までの直しを次の作文に持ち越し、同じ修正を繰り返させない。
- **`work/profile/`（`research-profile` / `key-findings` / `publications` / `methods` 等）があれば読む。** 申請書の「自己評価・研究遂行能力」や論文の自己引用・手法記述に使う。
- **引用は `work/papers/md/`（`raw-register` が登録した文献要約 md）を一次ソースにする。** 各 md の frontmatter（著者・年・誌名・DOI）から本文引用＋文献リストを組み立てる。登録が無いテーマなら「先に `raw-research` で探して `raw-register` で登録すると、その文献をそのまま引用できます」と促す（**実在しない引用を勝手に作らない**）。
- `work/topics/`（`raw-research` の文献リスト HTML）があれば背景のスコープ把握に使う。
- **数値は「事実の一覧」から書く。** 本文に使う数（測定値・計算値・文献値・条件・件数）を、書き始める前に `work/manuscripts/<doc-slug>/facts.md` に集める。1 行に 1 つ、**値・単位・何の値か・測定か計算か試算か・出どころ**（ファイルと行、図、論文）を書く。本文の数はここからだけ写し、記憶や会話から書かない（記憶で書いた言い換えは、数だけでなく「測ったのか試算か」「何と何の差か」までずれる）。一覧に無い数が要るときは、先に一次記録を開いて一覧に足す。
- 素材が足りなければ `raw-intake`（自分資料の取り込み）や `raw-register`（引用元の登録）を案内するか、最低限その場でヒアリングする。

### Step 3: 構成テンプレを選んでアウトライン

種別に応じた骨子を提示し、**ユーザーと合意してから本文に入る**（いきなり全文を書かない）。論文は IMRaD、申請書は制度様式、要旨は圧縮型。各セクションに「何を書くか」を 1 行で置いたアウトラインを先に作る。

### Step 4: 段階ドラフト（引用を挿入しながら）

- **アウトライン → セクション単位 → 全体**の順で書く。一度に全文を吐かず、セクションごとに提示して方向を確認できるようにする。
- **結論・主張先出し**を基本に、根拠（データ・引用）で支える。
- **引用は `work/papers/md/` の登録文献から**：本文引用（著者-年 or 番号、投稿先様式に合わせる）＋末尾の文献リストを生成。登録に無い主張は「**要出典**」と明示し、捏造しない。
- **字数・語数を必ずカウント**し、制限の範囲に収める（申請書は欄ごと）。生成後に字数を明示する（例:「Abstract 248 / 250 words」）。
- 物理量・分野の用語は正確に（単位・手法名・物質名の表記揺れを起こさない）。

### Step 5: 保存とチェック

- `work/manuscripts/<doc-slug>/` に保存（例 `work/manuscripts/adox-crystal-paper/`、`work/manuscripts/jsps-dc2/`）。**md 既定**。`.tex`/`.docx` は要望時（LaTeX 本文＋`references.bib`、または Word）。図は同フォルダか `work/figures/`。
- チェック: ① 字数オーバーが無いか ② 設問・投稿規程に答えているか ③ 引用が `work/papers/md/` と整合し、本文と文献リストが対応するか ④ 事実に反する誇張・未検証仮説の断定が無いか ⑤ **本文の数がすべて事実の一覧から来ているか**（下の照合を必ず回す）。
- **数値の照合（書き終えるたびに必ず）**：本文から数を機械で抜き出し、事実の一覧と照合する。LaTeX を章ごとのファイルに分けているなら、ファイルごとに回す。
  ```bash
  python3 ${SKILL}/scripts/check_numbers.py work/manuscripts/<doc-slug>/<本文> --facts work/manuscripts/<doc-slug>/facts.md
  ```
  - 対応: `.md` `.tex` `.txt` `.docx` `.pptx`。既定は小数と指数表記（1.2×10⁻³）だけを照合する（整数は年・図番号と混ざるので、件数なども確かめたいときだけ `--integers`）。事実の一覧が複数あれば `--facts` を重ねる
  - **一覧に無い数** → 一次記録を開いて値を引き直し、出どころつきで一覧に足してから本文を直す。**指数だけ違う・符号が違う** → 一覧の書き方の違い（「6.36、2.08 ×10⁻⁵」のように指数を最後にだけ書いた等）か、原稿の誤りかを確かめる。**丸め方が合わない**（四捨五入では合わず、切り上げか切り捨てでしか合わない）→ 丸め方を直すか、上限・下限として書いたなら「≤」「以下」などを付ける
  - **丸めて一致**（四捨五入で一致）・**不等号つきの丸め**（上限「≤ 0.64」「0.64 以下」は一覧の値の切り上げ、下限「≥ 0.63」「0.63 以上」は切り捨てで一致）は通る。向きの逆の不等号は「丸め方が合わない」。一覧の整数は、原稿の小数（2.0 など）の裏付けにならない（小数で書くなら一覧にも小数で書く）
  - 原稿から数が 1 つも取れないと終了コード 2（読めない形式か、小数が無い。整数も確かめるなら `--integers`）。小数点をカンマで書いた箇所（0,52）は照合できないので「（参考）」として挙がる。小数点はピリオドで書く
  - **「（参考）読まなかった小数」**は、図表の番号・版番号・識別子・組版の長さと判断して照合しなかった数。本文の値が混ざっていないかを目で確かめる（混ざっていたら、その数の前後の書き方を直すか、ユーザーに伝える）
  - 一覧の側に不等号がある数（「検出限界 < 0.05」）は、原稿でも同じ向きの不等号で書いた数だけを裏付ける
  - 読まないもの: 図・表・行の番号（Fig. 3・表 2・line 42）、日付、文献番号 [12]、版番号、URL・DOI、LaTeX の組版の指定（図の幅・色・行間など）
  - 終了コードが 0（全部たどれた）になってから「書けた」と報告する。数が合っても、**一覧のその行の「何の値か・測定か試算か」と本文の言い方が合っているか**は人が読んで確かめる（機械は意味まで見ない）
- **申請書の追加ガード**（メモリ feedback の一般則を内蔵）：
  - 他分野の審査員にも分かる**平易な日本語**（専門用語は初出で補足、略号の濫用を避ける）
  - **未検証の仮説を誇張しない**（「定量化する」等の断言を避け、「考察する／比較を試みる」など試行的表現を選ぶ）
  - **数値（応募総額・期間・字数・締切・実験値）は一次資料で確認**し、出典を添える
  - 引用は文中言及形式（`[n]` 番号の羅列を避ける）

### Step 6: 推敲ループ＋レビュー

- ユーザーの修正指示（「もっと簡潔に」「主張を弱めて」「200 字削って」「査読者 2 の指摘に答える形に」）で再生成。毎回字数を再カウントして提示する。
- **英文・引用整合のクロスチェック**：基本線は**各 CLI 単体の自己レビュー**で ①〜④（英文法・引用整合・主張の妥当性）を再点検する。**応用編（任意）**として、Codex CLI も併用しているなら推敲後に `codex:review` を回してもよい（追加プラグインは前提にしない）。
- **好みの学習（毎回・自分から確認）**：**推敲で修正を受けるたびに必ず**、その直しが汎用的な好み（語調・態・hedging・構成の癖・避ける語など、今後も繰り返し効くもの）か、その文書固有の一度きりの直しかを評価する。汎用的なら**ユーザーに言われるのを待たず自分から**「次回以降もこの直し方を既定にしますか？」と確認し、OK なら `work/manuscripts/_style/writing-preferences.md` に 1 行ルールとして追記する。**この挙動は Codex CLI / Claude Code / GitHub Copilot CLI で共通**。**一度きりの言い回し直しは記録しない**（聞きすぎない）。

## 文体プロファイル（`work/manuscripts/_style/`）

本人の過去論文から「書き方の癖」を抽出して再現する仕組み。**抽出本体は `raw-intake` が担当**（自分の論文 / CV / スライドから `work/manuscripts/_style/`・`work/profile/` を作る）。本スキルは執筆時に必ずそれを読んで踏襲する。文体プロファイルが無ければ `raw-intake` を案内するか、その場で過去論文を直接読む。**部署や `office/` の設定ファイル（`CLAUDE.md` / `AGENTS.md`）は書き換えない**（設定と文体を分離する）。

## 作文の好みの学習（`work/manuscripts/_style/writing-preferences.md`）

`raw-intake` が作る文体プロファイル（過去文書からの一括抽出＝初期文体）に対し、こちらは**会話中の推敲からの逐次学習**。推敲で繰り返し現れる好み（態・語調・hedging・構成・避ける語）を、**確認のうえ** 1 行ルールで追記し、次回以降の Step 2 で先回り適用する。これで「毎回同じ直しを頼む」状態を解消する（計算側の raw-input ↔ raw-playbook 学習ループの作文版）。

- 記録は**汎用的な好みのみ**。その文書固有の言い回し修正は記録しない
- 追記前に「次回以降も既定にしますか？」と確認（誤ルールは全作文を劣化させるため）
- 既存ルールと矛盾する新ルールは、確認のうえ**後発を優先**で更新する
- `office/` の設定ファイル（`CLAUDE.md` / `AGENTS.md`）は書き換えない（設定と好みを分離）

## 他スキルとの関係

- **`raw-intake` →（上流）** `work/manuscripts/_style/`（文体）・`work/profile/`（プロフィール）を供給。raw-write が消費する。
- **`raw-research` → `raw-register` → `raw-write`**：探す → 登録 → 引用して書く。raw-write は `work/papers/md/` の登録文献を引用源にする。
- **`raw-slides` は兄弟（下流）**：成果を発表に。要旨を raw-write が書き、論文紹介・発表スライドを raw-slides が作る。
- **`raw-register` と分離**：raw-register＝他者の論文を読む / 登録、raw-write＝自分の論文を書く（就活の `raw-research`＝調べる / `raw-es`＝書く と同じ分け方）。

## 重要な注意事項

- **引用を捏造しない**。本文の引用は `work/papers/md/` 登録文献に裏付けのあるものだけにする。無ければ「要出典」と明示し、`raw-register` での登録を促す
- **字数は絶対**。超過は必ず指摘し、収まるまで削る（テキストの字数の話なので誤魔化さない）
- **嘘・誇張・未検証仮説の断定を書かない**。データと文献の範囲で書く（特に申請書）
- **数値は事実の一覧（`facts.md`）からだけ書き、書き終えたら `check_numbers.py` で照合する**（終了コード 0 まで）
- **本人の文体を踏襲する**。`work/manuscripts/_style/` があれば必ず読む。生成後に文体の合致も確認する
- **推敲で汎用的な直しを受けたら、言われる前に自分から確認のうえ `writing-preferences.md` に蓄積し、次の作文に持ち越す**（毎回評価する・全 CLI 共通・一度きりの直しは記録しない）
- 成果物は **必ず `work/manuscripts/` 配下**（`office/` 配下に書かない）。既存ファイルは上書きせず、同名なら日付や `_v2` で分ける
- **本文・要約はユーザーの言語**で書く（論文は英語が既定でも、ユーザーが日本語を望めば日本語）
- **分野の用語・単位は正確に**（手法名・物質名・単位の表記揺れを起こさない）
